# 봇 서버를 여러 벌로 늘릴 때는 샤드 묶음마다 한 벌씩 맡긴다 (설계만)

- 상태: 채택
- 날짜: 2026-11-23

봇 서버는 한 벌만 띄웁니다(ADR 0059). 디스코드 게이트웨이 연결, 길드마다 음성 연결과 재생 순서, 음성 채널 상태(누가 어느 채널에 있는지)가 모두 파드 메모리에 있고, 같은 봇 토큰으로 두 벌이 같은 샤드에 붙으면 명령이 두 번 처리되고 음성 연결을 서로 끊기 때문입니다. 디스코드 서버가 늘면 언젠가 한 벌로 모자랍니다. 그때 무엇을 바꿀지 미리 적어 두어, 지금 코드가 그 길을 막지 않게 합니다. 이 ADR 이 정하는 것은 늘릴 때의 방식과 지금 지킬 것이고, 코드는 아래 신호가 보일 때 만듭니다.

## 신호

다음 중 하나가 보이면 이 설계로 만듭니다.

- 봇이 들어간 디스코드 서버가 2,000개를 넘는다. 디스코드는 2,500개부터 샤드를 나누라고 강제합니다.
- 한 벌의 CPU 나 메모리가 한도에 닿는다(Grafana 의 JVM 힙, 파드 CPU).
- quick chat 빠르기 95% 값(ADR 0053)이 늘어나는데 원인이 synthesis 서비스가 아니다(추적으로 가른다, ADR 0063).

## 설계

1. **봇 서버를 StatefulSet 으로 바꾸고, 파드 번호마다 샤드 묶음을 맡깁니다.** 예: 샤드 8개, 파드 2벌이면 0번 파드가 샤드 0~3, 1번 파드가 4~7. JDA 의 `setShardsTotal(8)` 과 `setShards(...)` 로 정하고, 파드 번호는 StatefulSet 이 붙이는 이름 끝 번호(`bot-server-0`)에서 읽습니다. 샤드 수는 디스코드 권장값을 쓰지 않고 고정합니다. 샤드 수를 바꾸면 모든 파드를 다시 켜야 합니다.
2. **길드를 맡은 파드는 계산으로 압니다.** 디스코드 규칙 `(guild_id >> 22) % 샤드 수` 로 샤드를 구하고, 샤드로 파드 번호를 구합니다.
3. **quick chat 은 사용자의 음성 채널을 아는 파드가 처리해야 합니다.** 데스크톱 앱은 디스코드 서버를 모르고 사용자만 보내므로, 음성 상태 소식을 받을 때 "사용자 → 길드, 채널" 표를 공유 저장소(Redis)에 씁니다. 요청을 받은 파드는 표에서 길드를 찾아, 자기 샤드가 아니면 맡은 파드(헤드리스 Service 의 `bot-server-1.bot-server`)로 넘깁니다.
   - 지금 `BotVoiceStateMemoryAdapter` 와 음성 상태 출력 포트(`VoiceStatePort`) 뒤에 있어서, 바뀌는 곳은 어댑터와 넘기기 어댑터입니다.
4. **한 번만 할 일은 0번 파드만 합니다.** 슬래시 명령 등록(`DiscordListenerRegistrar`), 켜질 때 허용 목록 정리처럼 봇 전체에 한 번이면 되는 일입니다.
5. **업데이트는 파드 하나씩 내렸다 올립니다**(StatefulSet 의 `OrderedReady`). 그 파드가 맡은 샤드의 길드만 잠깐 끊깁니다.
6. **더 커지면** 게이트웨이 연결만 맡는 프로세스를 두고 이벤트를 메시지 큐로 일꾼에게 나누는 방식이 큰 디스코드 봇에서 흔합니다. 다만 음성 연결은 샤드를 맡은 프로세스에 묶여 있어서, 음성 봇은 위의 샤드 묶음 방식이 먼저입니다.

## 지금 지키는 것

- 길드마다의 상태는 지금처럼 출력 포트 뒤(어댑터)에 둡니다. 서비스나 도메인이 메모리의 전역 상태를 직접 들고 있지 않게 합니다.
- 디스코드 연결은 처음부터 `ShardManager` 로 만듭니다(ADR 0046).
- 연결 코드처럼 파드끼리 나눠 봐야 하는 값은 DB 에 둡니다(ADR 0049).

## 고르지 않은 것

- 봇 서버를 Deployment 로 여러 벌 띄우고 HPA 로 늘리기: 샤드를 나눠 맡기지 않으면 같은 샤드에 두 벌이 붙습니다.
- 컨텍스트마다 서비스로 나누기: speech 는 디스코드 음성 연결이 있는 프로세스에 있어야 해서 나눠도 샤드 문제는 그대로입니다.
