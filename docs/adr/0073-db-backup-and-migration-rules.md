# DB 는 하루에 한 번 덤프하고, 마이그레이션은 늘리기와 줄이기를 다른 판에 나눈다

- 상태: 채택
- 날짜: 2026-11-28

배포 DB 에는 기기 등록, 목소리 설정, 허용 목록이 있습니다. compose 의 `mysql-data` 볼륨, 쿠버네티스의 PVC 모두 따로 남기는 곳이 없어서 디스크가 망가지면 모든 사용자가 `/연결` 부터 다시 해야 했습니다. 되살리는 방법을 연습한 적도 없었습니다.

Flyway 는 서버가 켜질 때 돌고(ADR 0016), 무료판에는 되돌리는 파일이 없습니다. 그런데 앱을 옛 판으로 되돌릴 때 새 스키마와 맞는지 정한 규칙이 없었습니다. 또 `baseline-on-migrate: true` 가 운영 MySQL 에도 켜져 있었습니다. Flyway 전에 만든 옛 H2 파일을 이어 받으려고 둔 것인데, 비어 있지 않은 엉뚱한 DB 에 붙으면 V1 을 건너뛰고 그 위에 쌓습니다.

## 결정

1. **하루에 한 번 `mysqldump` 를 gzip 으로 남기고 14일치를 둡니다.**
   - 이 PC 배포: `compose.prod.yaml` 의 `mysql-backup` 이 띄우자마자 한 번, 그 뒤 24시간마다 `QUICKTTS_BACKUP_DIR`(기본 `./backups`)에 씁니다. 이 폴더를 OneDrive·Google Drive 처럼 PC 밖으로 올라가는 폴더로 두기를 권합니다.
   - 쿠버네티스: `mysql-backup` CronJob 이 매일 04:30(서울)에 DB 와 다른 PVC(`mysql-backup`)에 씁니다.
   - `--single-transaction` 으로 서버를 멈추지 않고 한 시점의 모습을 뜹니다. 다 쓴 뒤에만 `.sql.gz` 이름을 붙여서 덜 쓴 파일이 백업처럼 보이지 않게 합니다.
2. **되살리기 연습은 `scripts/restore-drill.sh` 로 합니다.** 덤프 하나를 잠깐 띄운 빈 MySQL 에 넣고 표마다 줄 수와 마지막 마이그레이션 판을 보여 줍니다. 되살리는 순서는 `docs/runbook.md` 에 둡니다.
3. **마이그레이션은 늘리기(expand)와 줄이기(contract)를 다른 판에 나눕니다.** 바로 앞 판의 서버가 새 스키마에서도 돌아야 이미지 태그만 바꿔 되돌릴 수 있습니다.
   - 열·표를 더하는 판: 새 열은 비어도 되거나 기본값이 있어야 합니다. 앞 판은 새 열을 모르고 씁니다.
   - 옮기는 판: 새 코드가 새 열을 읽고 씁니다.
   - 줄이는 판: 앞 판도 더는 쓰지 않는 것을 지웁니다. 지우거나 이름·타입을 바꾸는 파일은 `V<n>__contract_<설명>.sql` 로 이름을 붙입니다. `MigrationRulesTest` 가 이름을 확인합니다(이 규칙 전에 만든 V5 까지는 보지 않음).
4. **`baseline-on-migrate` 는 기본으로 끕니다.** 기록 없이 표가 있는 DB 에 붙으면 켜지지 않습니다. Flyway 전(2026-10-18) 옛 H2 파일만 처음 한 번 `QUICKTTS_FLYWAY_BASELINE_ON_MIGRATE=true` 로 이어 받습니다.

## 결과

- 이 PC 가 망가져도 백업 폴더가 PC 밖에 있으면 최대 하루 치만 잃습니다.
- 쿠버네티스 백업은 아직 클러스터 안에 있습니다. 클러스터를 실제로 띄울 때 오브젝트 저장소로 보내는 일을 더합니다.
- 컬럼 하나를 지우는 데 판이 두 번 필요합니다.
- `__contract_` 마이그레이션이 들어간 판보다 앞으로 되돌릴 때는 DB 도 그 전 덤프로 되살립니다.
- 옛 H2 파일을 그대로 켜면 고치는 방법이 담긴 Flyway 오류로 멈춥니다.

## 고르지 않은 것

- 관리형 DB 의 자동 백업: 지금 배포는 PC 의 MySQL 컨테이너입니다. 관리형으로 옮기면 그쪽 백업을 쓰고 이 컨테이너를 뺍니다.
- 바이너리 로그로 시점 되살리기(PITR): 하루 치를 잃어도 사용자가 `/연결` 만 다시 하면 되는 데이터라 설정과 연습 비용이 더 큽니다.
- Flyway 유료판의 되돌리기 파일: 되돌리기 파일도 시험해야 하고, 늘리기·줄이기를 나누면 필요 없습니다.
