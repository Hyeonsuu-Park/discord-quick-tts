# 나눠 준 앱이 깨지지 않게 API 차이를 CI 가 검사하고, 최소 앱 판은 응답 헤더로 알린다

- 상태: 채택
- 날짜: 2026-11-28

서버는 언제든 새 판으로 바꿀 수 있지만, 나눠 준 exe 는 옛 판이 사용자 PC 에 오래 남습니다. 지금까지 서버와 앱은 `libs/api-contract` 를 같은 커밋으로 써서, 옛 앱과 새 서버가 맞는지는 아무도 보지 않았습니다. 앱이 너무 오래되었을 때 알릴 길도, 지금 어떤 판이 쓰이는지 볼 길도 없었습니다.

## 결정

1. **API 약속을 파일로 남깁니다.** `libs/api-contract/openapi.json` 은 springdoc 이 컨트롤러에서 만든 문서(ADR 0054)에서 서버 주소만 뺀 것입니다. 통합 테스트가 지금 문서와 이 파일이 같은지 보고, API 를 바꾼 PR 은 `-PupdateOpenApi` 로 파일을 다시 만들어 함께 커밋합니다. PR 화면에서 API 가 어떻게 바뀌었는지 이 파일의 차이로 봅니다.
2. **요청·응답 record 의 필드는 모두 필수로 적고, null 일 수 있는 필드는 `@Nullable` 로 표시합니다.** 서버는 record 필드를 null 까지 늘 싣고 다니므로 사실과 같습니다. 이렇게 적어야 아래 검사가 "응답에서 필드 빼기"와 "요청에 필수 필드 더하기"를 깨는 변경으로 잡습니다.
3. **CI 가 main 의 약속과 PR 의 약속을 oasdiff 로 비교해 깨는 변경이 있으면 막습니다.** `/api/v1` 안에서는 경로, 응답 필드, 선택 요청 필드, 오류 코드를 더하기만 합니다. 빼거나 바꿔야 하면 `/api/v2` 를 함께 띄웁니다(ADR 0013).
4. **옛 판 경로를 내릴 때는 최소 앱 판을 먼저 올립니다.** 서버 설정 `QUICKTTS_MINIMUM_CLIENT_VERSION`(예 `0.4.0`)을 정하면 `/api` 응답마다 `X-QuickTTS-Minimum-Client-Version` 헤더가 붙고, 그보다 낮은 앱은 트레이 알림으로 가장 최근 Release 를 안내합니다. 옛 앱이 줄어든 뒤 깨는 변경을 `libs/api-contract/openapi-breaking-allowed.txt` 에 한 줄씩 적어 CI 를 넘깁니다.
5. **앱은 요청마다 `User-Agent: QuickTTS/<판>` 을 보내고, 서버는 판마다 `quicktts.client.requests` 로 셉니다.** 최소 판을 올리기 전에 아직 옛 판을 쓰는 사람이 얼마나 되는지 봅니다. 태그 값은 `1.2.3`, `dev`, `other` 모양만 씁니다.

## 결과

- 나눠 준 앱을 깨는 변경이 PR 에서 막히고, 일부러 깰 때는 기록(허용 파일)이 남습니다.
- 서버가 앱을 거절하지는 않습니다. 알림을 무시한 옛 앱은 깨는 변경이 들어간 날부터 오류를 봅니다. 꼭 막아야 하는 보안 문제가 생기면 그때 426 으로 거절하는 쪽을 따로 정합니다.
- API 를 바꾸는 PR 은 약속 파일을 다시 만드는 단계가 하나 늡니다.
- 오류 코드 문자열(`ApiErrorCode`)은 OpenAPI 에 값으로 적혀 있지 않아 검사가 보지 않습니다. 빼거나 이름을 바꾸지 않는 규칙으로 지킵니다.

## 고르지 않은 것

- 서버를 띄워 옛 앱 판의 시험을 돌리기(소비자 주도 계약 시험, Pact 등): 앱이 하나이고 API 가 셋이라 도구와 브로커를 두는 값이 큽니다.
- 약속 파일을 사람이 먼저 쓰고 코드를 만들기(설계 우선): 지금은 컨트롤러가 기준이고 springdoc 이 이미 문서를 만듭니다.
- 앱이 켜질 때 따로 "최소 판" API 를 부르기: 요청이 하나 늘고, 이미 받는 응답의 헤더로 충분합니다.
