# 디스코드 명령과 봇 서버 켜기는 synthesis 서비스를 기다리지 않는다

- 상태: 채택
- 날짜: 2026-11-28

목소리 목록은 synthesis 서비스가 압니다(ADR 0065). 봇 서버는 이 목록을 두 곳에서 HTTP 로 받았습니다.

- 켜질 때: `DiscordListenerRegistrar` 가 `@PostConstruct` 에서 슬래시 명령 정의를 만들며 `/목소리` 의 선택지를 받았습니다. synthesis 가 떠 있지 않으면 봇 서버가 켜지지 않았습니다. 쿠버네티스에는 켜지는 순서가 없고, ADR 0062 결정 6("서비스가 잠깐 없어도 봇 서버는 명령을 계속 받아야 한다")과도 맞지 않았습니다. 목소리를 바꿔도 봇을 다시 켜야 선택지가 바뀌었습니다.
- `/목소리` 를 칠 때: JDA 는 따로 정하지 않으면 게이트웨이 소식을 읽는 스레드에서 리스너를 부릅니다. 그 스레드에서 HTTP 를 기다리고 응답을 미루지 않았습니다. synthesis 가 3초 넘게 걸리면 디스코드가 "애플리케이션이 응답하지 않았어요" 를 띄우고, 그동안 그 샤드의 음성 상태 소식도 멈췄습니다.

## 결정

1. **목소리 목록은 마지막으로 받은 값을 들고 있다가 돌려주고, 1분마다 새로 받습니다.** 출력 어댑터(`VoiceChoicesSynthesisAdapter`)가 들고 있습니다. 새로 받지 못하면 마지막 목록을 그대로 쓰고 경고 로그를 남깁니다. 한 번도 받지 못했을 때만 그 자리에서 묻습니다.
2. **슬래시 명령은 켜질 때가 아니라 켜진 뒤 1분마다 만들어 봅니다.** 정의가 지난번에 올린 것과 같으면 보내지 않고, 다를 때만 디스코드에 올립니다. 정의를 만들지 못하면(synthesis 가 아직 없음) 다음에 다시 합니다. 디스코드는 전에 올린 명령을 그대로 들고 있으므로 그동안에도 명령은 됩니다. 리스너 등록은 지금처럼 켜질 때 합니다.
3. **`/목소리` 는 먼저 응답을 미룹니다(`deferReply`).** 답은 후속 메시지로 보냅니다. `InteractionErrorHandler` 도 이미 응답한 명령이 실패하면 후속 메시지로 안내해서, 미뤄 둔 명령이 "생각하는 중" 에 머물지 않게 합니다.
4. **JDA 의 이벤트 스레드 풀은 바꾸지 않습니다.** 음성 상태 소식은 들어온 순서대로 처리해야 봇 자리(ADR 0014) 판단이 맞습니다. 대신 이벤트 스레드에서 바깥 서비스를 기다리는 일 자체를 없앱니다(결정 1).

## 결과

- synthesis 가 없어도 봇 서버가 켜지고, 디스코드 명령과 웹 API 도 받습니다. quick chat 은 지금처럼 `speech-synthesis-failed` 로 실패합니다.
- 목소리를 synthesis 에 더하거나 빼면 1분 안에 `/목소리` 선택지가 바뀝니다. 봇을 다시 켤 일이 없습니다.
- 목소리 목록이 최대 1분 늦게 반영됩니다. 그 사이 없어진 목소리를 고르면 synthesis 가 이 목소리를 모른다고 실패하고 Google 번역 목소리로 대신 읽습니다(ADR 0006).
- `@EnableScheduling` 을 켭니다(`config/SchedulingConfig`).

## 고르지 않은 것

- JDA `setEventPool` 로 모든 리스너를 스레드 풀에서 돌리기: 이벤트 순서가 섞입니다(결정 4).
- 목소리 목록을 봇 서버 설정이나 DB 에 적어 두기: 목소리를 아는 곳이 둘이 됩니다.
- 켜질 때 synthesis 를 기다렸다가 켜기(initContainer, depends_on): compose 에서는 되지만 쿠버네티스에서 synthesis 가 다시 뜨는 동안에도 봇이 켜지지 못합니다.
