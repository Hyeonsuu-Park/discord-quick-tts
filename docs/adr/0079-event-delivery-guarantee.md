# 이벤트는 지금 커밋 뒤 최대 한 번 전달하고 켜질 때 다시 맞추며, 프로세스를 나누면 outbox 로 보낸다

- 상태: 채택
- 날짜: 2026-11-28

ADR 0040 은 보내는 쪽 서비스가 `...EventPort` 로 이벤트를 내고, 지금은 스프링 이벤트로, 나중에 프로세스를 나누면 Kafka 같은 메시지 브로커로 보내며 "서비스는 어느 쪽인지 모른다"고 적었습니다. 이벤트가 얼마나 확실히 전달되는지는 어디에도 적혀 있지 않았고, 브로커로 옮길 때 서비스가 모른다는 말은 사실과 다릅니다.

지금 이벤트는 `GuildRemovedFromAllowlist` 하나입니다. `GuildAllowlistEventAdapter` 가 스프링 이벤트로 내고, `GuildRemovedFromAllowlistListener` 가 `@TransactionalEventListener` 로 받아 커밋 뒤 같은 스레드에서 봇을 그 서버에서 내보냅니다. 커밋 뒤 디스코드 호출이 실패하거나 그 순간 프로세스가 죽으면 다시 하지 않습니다. 그래도 봇이 켜질 때 `GuildJoinListener.leaveNotAllowedGuildsOnStartup` 이 허용 목록에 없는 서버를 모두 다시 나가므로 결과는 맞춰집니다.

## 결정

1. **같은 프로세스 안의 이벤트는 커밋 뒤 최대 한 번(at-most-once) 전달합니다.** 받는 쪽의 결과는 이벤트만 믿지 않고, 켜질 때나 주기적으로 DB 상태에서 다시 맞추는 길(reconciliation)을 함께 둡니다. 그런 길이 없는 이벤트를 새로 만들면 이 ADR 을 다시 봅니다.
2. **받는 쪽은 같은 이벤트를 두 번 받아도 결과가 같게(멱등) 만듭니다.** 지금 받는 쪽인 "허용 목록에 없으면 나가기"는 이미 나간 서버면 아무것도 하지 않습니다.
3. **프로세스를 나눠 브로커로 보낼 때는 transactional outbox 를 씁니다.** DB 에 쓰기와 브로커에 보내기는 따로 성공하거나 실패할 수 있습니다(이중 쓰기). 그래서 보내는 쪽 서비스의 트랜잭션 안에서 이벤트를 outbox 표에 함께 쓰고, 따로 도는 발행기가 커밋된 줄을 브로커로 보냅니다. 전달은 최소 한 번(at-least-once)이 되므로 2번의 멱등이 꼭 필요합니다. 공개 이벤트 record 가 메시지 모양이 되는 것(ADR 0040)은 그대로입니다.
4. **그때 바뀌는 곳**: `...EventAdapter` 가 브로커 대신 outbox 표에 쓰는 저장 어댑터가 되고, 보내는 쪽 서비스는 이벤트 내기가 트랜잭션 안에 있어야 합니다(지금은 `@Transactional` 이 있는 서비스에서만 냅니다, ADR 0033). 서비스 코드는 거의 그대로지만 "어느 쪽인지 모른다"가 아니라 "트랜잭션 안에서 낸다"가 지켜야 할 조건입니다.

## 결과

- 지금 코드는 바뀌지 않습니다. 이벤트의 전달 보장과 그것을 메우는 길이 문서에 남습니다.
- ADR 0040 의 "나중에 Kafka 로 보내도 서비스는 모른다"는 이 ADR 의 3·4번으로 바뀝니다.
- outbox 표, 발행기, 받는 쪽 중복 거르기는 프로세스를 나누는 날 만듭니다. Spring Modulith 의 이벤트 발행 기록처럼 같은 일을 하는 라이브러리도 그때 고릅니다.

## 고르지 않은 것

- 지금 outbox 를 만들기: 받는 쪽이 같은 프로세스이고 켜질 때 다시 맞추므로, 표와 발행기가 늘어나는 만큼 얻는 것이 없습니다.
- 브로커에 바로 보내기(커밋 뒤 보내기): 커밋 뒤 보내기가 실패하면 이벤트를 잃고, 커밋 전에 보내면 롤백된 일을 알리게 됩니다.
