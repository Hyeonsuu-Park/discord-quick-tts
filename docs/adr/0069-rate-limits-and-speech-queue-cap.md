# 웹 API 는 사용자·IP 마다 1분 상한을 두고, 디스코드 서버마다 읽을 차례는 20개까지 받는다

- 상태: 채택
- 날짜: 2026-11-28

기기 토큰을 가진 사람이 스크립트로 문장을 몰아 보내도 막는 것이 없었습니다. 재생 순서(`GuildSpeechQueue`)는 끝이 없는 큐라서 메모리가 차고, 문장마다 synthesis 서비스와 비공식 TTS 엔진을 부르므로 엔진이 우리 서버를 막을 수도 있습니다. 토큰 없이 받는 기기 등록도 횟수 제한이 없었습니다. ADR 0067 결과에 "모르는 사람에게 나눠 주기 전에 사용량 제한이 필요" 라고 적어 두었습니다.

이것은 사용자 화면의 도배 방지 기능(연달아 보내는 것을 막고 안내하기)이 아닙니다. 평소 쓰는 사람은 닿지 않는 높은 값으로 서버를 지키는 상한입니다.

## 결정

1. **웹 API 사용량 제한은 앱 안의 토큰 버킷(Bucket4j)으로 셉니다.** 봇 서버는 한 벌만 뜨므로(ADR 0059) 버킷은 프로세스 메모리에 두고, 10분 동안 안 쓴 버킷은 Caffeine 이 지웁니다.
   - 기기 토큰이 있는 `/api/` 요청: 디스코드 사용자마다 1분에 60번. 한 사람이 PC 를 여럿 연결해도 같이 셉니다.
   - 기기 등록(`POST /api/v1/devices`): 보낸 곳(IP)마다 1분에 10번. Cloudflare Tunnel 뒤에서는 `CF-Connecting-IP` 헤더가 보낸 곳입니다.
   - 상태 확인, API 문서는 세지 않습니다.
   - 값은 `quicktts.rate-limit.*`(`QUICKTTS_RATE_LIMIT_REQUESTS_PER_MINUTE`, `QUICKTTS_RATE_LIMIT_REGISTRATIONS_PER_MINUTE`)로 바꿉니다.
2. **세는 자리는 웹 인바운드 어댑터의 필터(`shared/adapter/in/web/RateLimitFilter`)입니다.** 기기 토큰 인증 필터 바로 뒤에 돌아서 누가 보냈는지 압니다. 유스케이스와 도메인은 모릅니다.
3. **디스코드 서버마다 읽을 차례를 기다리는 문장은 20개까지 받습니다.** 넘으면 출력 어댑터가 `SpeechQueueFullException` 을 던집니다. 한 문장이 길어야 몇 초라서, 그보다 많이 쌓이면 대화에 쓰는 속도가 아니고 뒤 문장은 몇 분 뒤에야 읽힙니다.
4. **둘 다 새 종류 `RESOURCE_EXHAUSTED`(gRPC 표준 코드, ADR 0044)로 알리고 웹은 429 로 답합니다.** 오류 코드는 `too-many-requests`(`Retry-After` 헤더에 기다릴 초), `speech-queue-full` 입니다. 데스크톱 앱은 이 코드로 안내 문구를 고릅니다.

## 결과

- 토큰 하나로 1분에 보낼 수 있는 문장이 60개로 묶여서, TTS 엔진을 부르는 양에도 위쪽 끝이 생깁니다.
- 옛 데스크톱 앱은 두 코드를 몰라서 "봇 서버 오류(HTTP 429)" 로 보여 줍니다. 평소 쓰는 양에서는 생기지 않습니다.
- 봇 서버를 여러 벌로 늘리면(ADR 0064) 벌마다 따로 세므로, 그때는 Redis 같은 공유 저장소의 버킷으로 바꿉니다. 필터 안만 바뀝니다.
- `CF-Connecting-IP` 는 터널을 거치지 않고 봇 서버에 바로 닿는 곳(이 PC 안)에서는 꾸밀 수 있습니다. 바깥은 터널로만 닿으므로(ADR 0068) 괜찮습니다.

## 고르지 않은 것

- Cloudflare 의 사용량 제한 규칙: 계정과 도메인이 있는 named tunnel 이어야 쓸 수 있고, 기기 토큰이 아니라 IP 로만 셉니다. named tunnel 로 바꾸면 기기 등록 제한은 그쪽에 더할 수 있습니다.
- 손으로 만든 카운터: 1분 창 경계에서 두 배가 지나가는 고정 창이 되기 쉽고, 다시 차는 계산을 직접 시험해야 합니다.
- 유스케이스에서 세기: 웹 요청만의 일인데 디스코드 명령과 서비스가 모두 알게 됩니다.
