# 데스크톱 앱은 기기 토큰을 Windows DPAPI 로 암호화해 설정 파일에 적는다

- 상태: 채택
- 날짜: 2026-11-28

기기 토큰은 그 PC 에서 누구의 이름으로 문장을 읽힐지 정하는 값입니다. 지금까지는 사용자 홈의 `client.properties` 에 평문으로 있어서, 그 파일이 백업, 클라우드 동기화 폴더, 원격 지원 화면, 다른 프로그램을 거쳐 새면 그대로 쓸 수 있었습니다.

## 결정

1. **Windows 에서는 기기 토큰을 DPAPI(`CryptProtectData`)로 암호화해 `device-token=dpapi:<Base64>` 로 적습니다.** 열쇠는 Windows 가 로그인한 사용자 계정에 묶어 관리하므로 같은 PC 의 같은 사용자만 풉니다. 앱이 열쇠 파일이나 비밀번호를 따로 두지 않습니다.
2. **DPAPI 는 자바 FFM 으로 부릅니다.** 이미 `WindowsForeground` 가 같은 방식으로 user32 를 부르고 있어서 JNA 같은 의존성을 늘리지 않습니다. 다른 프로그램이 DPAPI 로 감싼 값과 섞이지 않게 앱 고유의 엔트로피를 더합니다.
3. **예전 판이 평문으로 적은 토큰은 읽은 뒤 바로 암호화해 다시 적습니다.** 사용자가 할 일은 없습니다.
4. **풀 수 없는 토큰은 연결하지 않은 것으로 봅니다.** 다른 PC 나 다른 사용자에게서 복사한 파일이면 디스코드 `/연결` 을 다시 하게 됩니다.
5. **Windows 가 아닌 개발 PC(Gradle `run`)는 평문 그대로 적습니다.** DPAPI 시험은 Windows 에서만 돌고, CI 의 설치 파일 작업(windows-latest)에서 돌립니다.

## 결과

- 설정 파일만 새어서는 토큰을 쓸 수 없습니다. 같은 사용자로 도는 악성 프로그램은 여전히 풀 수 있습니다. 그 경우는 디스코드 `/연결해제` 로 끊습니다.
- Windows 를 다시 설치하거나 사용자 계정을 새로 만들면 `/연결` 을 다시 해야 합니다.
- 설정 파일을 손으로 열어 토큰을 확인할 수 없습니다. 확인할 일이 생기면 `/연결` 을 다시 합니다.

## 고르지 않은 것

- Windows 자격 증명 관리자(Credential Manager)에 넣기: 안에서는 같은 DPAPI 를 쓰고, 부르는 함수와 정리할 항목이 늡니다. 설정이 파일 하나에 모여 있는 편이 지금 앱 구조와 맞습니다.
- 앱이 만든 열쇠로 직접 암호화하기: 열쇠를 어디에 둘지가 같은 문제로 돌아옵니다.
- java-keyring, JNA 같은 라이브러리: 함수 세 개를 부르려고 의존성이 늡니다.
