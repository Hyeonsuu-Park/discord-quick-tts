# 이미지는 CI 를 통과한 main 커밋만 올리고, 올리기 전에 한 번 띄워 본다

- 상태: 채택
- 날짜: 2026-11-28

이미지 워크플로(`images.yml`, ADR 0058)와 CI(`ci.yml`)가 서로 따로 돌았습니다. main 에서 테스트가 깨져도 `:main` 과 `:main-<커밋>` 이미지가 올라갔고, 운영 compose 는 그 태그를 받습니다(ADR 0068). 또 만든 이미지를 한 번도 띄워 보지 않아서, 읽기 전용 파일 시스템이나 root 아닌 사용자처럼 실행할 때만 나는 문제는 배포해야 알 수 있었습니다.

## 결정

1. **main 이미지는 CI 가 부릅니다.** `ci.yml` 의 `images` job 이 빌드·테스트(`build`)와 매니페스트 검사(`k8s-manifests`)를 기다린 뒤 `images.yml` 을 재사용 워크플로(`workflow_call`)로 부릅니다. `images.yml` 은 main 푸시로는 따로 돌지 않습니다.
2. **올리기 전에 amd64 이미지를 띄워 봅니다(`scripts/smoke-image.sh`).** 쿠버네티스와 같은 조건(읽기 전용 루트, `/tmp` 만 쓰기, root 아닌 사용자)으로 띄우고 liveness 와 API 하나를 부릅니다. 실패하면 올리지 않고 컨테이너 로그를 Actions 결과물로 남깁니다. PR 에서도 같은 것을 합니다.
   - synthesis 서비스: `/internal/v1/voices`(바깥 TTS 를 부르지 않음)
   - 봇 서버: 디스코드에 붙어야 켜지므로 `SMOKE_DISCORD_TOKEN` 비밀값(시험용 봇 토큰)이 있을 때만 띄우고 `/actuator/health/readiness` 를 봅니다. 없으면 건너뛰고 알림만 남깁니다.
3. **띄워 볼 이미지와 올릴 이미지는 같은 빌드 캐시를 씁니다.** amd64 를 먼저 만들어 띄워 보고, 올리는 단계는 캐시에서 amd64 를 그대로 쓰고 arm64 만 더 만듭니다.
4. **`v*` 태그 이미지는 지금처럼 태그 푸시로 만듭니다(ADR 0020).** 태그는 main 에서 CI 가 통과한 커밋에 답니다. 태그 푸시에는 CI 가 돌지 않으므로 태그를 다는 사람이 main 의 CI 결과를 보고 답니다. 띄워 보기는 태그 이미지에도 합니다.

## 결과

- main 에 들어온 뒤 이미지가 나오기까지 빌드·테스트 시간(2~3분)만큼 늦어집니다.
- 이제 main 커밋마다 이미지가 나옵니다. 문서만 바꾼 커밋도 `:main-<커밋>` 이 생기지만 내용은 앞 커밋과 같습니다.
- 봇 서버 이미지까지 띄워 보려면 시험용 디스코드 봇을 하나 만들어 그 토큰을 저장소 비밀값 `SMOKE_DISCORD_TOKEN` 으로 넣습니다. 운영 봇 토큰은 쓰지 않습니다(같은 토큰으로 두 곳이 붙으면 운영 봇이 끊깁니다).

## 고르지 않은 것

- `workflow_run` 으로 CI 가 끝나면 이미지 워크플로 돌리기: 실패한 CI 에도 돌아서 결과를 따로 확인해야 하고, PR 화면에서 둘의 관계가 보이지 않습니다.
- 이미지 워크플로 안에서 테스트를 한 번 더 돌리기: 같은 테스트를 두 번 돕니다.
- 봇 서버를 가짜 토큰으로 띄워 디스코드 로그인 직전까지만 보기: 켜지다 실패하는 것이 정상이라 진짜 문제와 구분하기 어렵습니다.
